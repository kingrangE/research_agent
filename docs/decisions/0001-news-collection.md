# ADR 0001: 빠른 뉴스 발견과 정기 누락 점검을 분리한다

결정일: 2026-11-12. 상태: 사용자가 방향을 승인한 뒤 포털 수집·누적 기사 API·Airflow DAG와 로컬 Docker 실행을 구현했다. 최초 설계의 비교와 계획은 아래에 보존하며, 실제 적용 상태와 실행 중 발견한 실패·수정은 마지막 구현 기록에서 구분한다.

## 상황과 제품 요구

제품은 매매 중 국내·미국 주식의 판단을 바꿀 자료를 찾는 동시에, 사용자가 추천과 관계없이 직접 기사를 골라 읽을 수 있어야 한다. 기사 수집 여부와 추천 적합성은 별개의 판단이다. 상품 안내·행사·배경 기사·미분석 기사도 보관하고 전체 기사에서 볼 수 있어야 하며, 같은 사건의 서로 다른 원문은 추천용 대표 기사 묶기 때문에 사라져서는 안 된다.

포털 증권의 전체 기사 발견이 목표다. 종목이나 산업별 검색어만으로 수집하면 모르는 기업·새 테마·시장 충격을 놓칠 수 있다. 따라서 최신 전체 목록을 주 수집 경로로 검토하고 언론사 RSS와 검색 API는 보완 경로로 쓴다. 현재 전체 자료 화면은 최근 RSS 목록만 보여주므로 누적 보관 기사 조회·페이지 이동·기간 필터를 별도로 구현해야 한다.

기사 발행, 포털 제공, 최초 발견, 본문 확보, 분석 완료는 서로 다른 시각이다. 발견 주기를 줄여도 포털의 원본 반영과 본문·모델 처리 지연은 남는다. ‘10초마다 확인’과 ‘발행 10초 이내 도착 보장’을 같은 것으로 설명하지 않는다. 계약 취소·정정·실적 하향은 투자 판단을 바꾸므로 반복 기사나 오래된 기사로 잘못 숨기지 않아야 한다.

## 결정과 선택 이유

짧은 주기로 목록을 확인하는 상시 수집 작업자와, 정기적으로 누락을 대조하고 보충하는 Airflow 작업을 분리한다. 상시 작업자는 프로세스를 계속 실행한 채 요청·저장·대기를 반복한다. 새 기사 발견은 본문 다운로드나 LLM 추론의 완료를 기다리지 않는다. 수집과 분석은 대기열로 연결하고, 전체 기사 화면은 분석 완료 여부와 관계없이 보관소를 조회한다.

Airflow는 시작과 끝이 있는 점검·보충 작업의 실행 순서, 상태, 로그와 실패 재실행을 관리한다. 최신 목록과 최근 보관 자료 대조, 날짜별 기사 보충, 실패한 본문 작업의 재등록, 수집 품질 집계를 맡긴다. 상시 수집과 Airflow는 같은 식별·저장 규칙을 사용하며, 같은 기사를 다시 발견해도 중복 보관이나 분석 작업 증식을 일으키지 않아야 한다. 기사 전문은 작업 간 메시지에 복사하지 않고 저장소에 보관하고 식별자와 처리 구간을 전달한다.

이 선택은 Airflow가 초 단위 실행을 지원하지 않기 때문이 아니다. 시간 간격 일정은 지원하지만 실행 자원과 스케줄링의 영향을 받는다. 빠른 발견 경로에서 반복적인 작업 시작과 상태 관리 비용을 줄이고, 구간별 재실행이 중요한 업무에 Airflow를 쓰려는 선택이다. 실제 상대 지연과 운영 비용을 측정한 결과는 아직 없으므로 현재 판단을 성능 실험 결과로 제시하지 않는다.

## 비교한 대안

| 대안 | 장점 | 현재 선택하지 않은 이유와 재검토 조건 |
| --- | --- | --- |
| Airflow로 전체 수집을 실행 | 실행 이력·재시도·여러 수집원 관리가 한곳에 모임 | 분 단위 도착이면 충분할 때 적합한 대안이다. 짧은 반복 수집의 실제 실행 지연과 관리 비용을 측정한 뒤 단독 구성도 재검토한다. |
| 상시 작업자만 사용 | 구성과 실행 경로가 단순함 | 수집원과 복구 작업이 늘면 구간별 실행 이력·작업 의존성 관리를 직접 구현해야 한다. 초기에는 가능하지만 정기 보충 업무의 운영 요구가 커지면 Airflow로 분리한다. |
| 뉴스 검색 API만 사용 | 공식 인증·응답 형식을 사용할 수 있음 | 검색어와 조회 범위 때문에 포털 증권 전체 기사를 보장하지 못한다. 보조 발견 경로로 사용한다. |
| 처음부터 별도 메시지 브로커와 분산 처리 도입 | 여러 서버에서 작업 분배·확장이 쉬움 | 현재 단일 서버에는 운영 요소가 늘어난다. 기존 영속 대기열을 먼저 사용하고, 여러 호스트의 처리량·잠금 충돌이 실제 문제가 될 때 확장한다. |
| 계약된 뉴스 피드 사용 | 계약 범위에 따른 지연·재전송·사용 권한을 확인할 수 있음 | 초기 비용과 대상 매체 범위를 확인해야 한다. 무누락·지연 보장이 필수 요건이면 우선 검토하며 포털과 동일한 기사 범위라고 가정하지 않는다. |

## 강제하는 조건과 조정 가능한 설정

수집·추천 분리, 처리 완료 전 기사 공개, 원문 식별자 보존, 재실행의 중복 방지, 저장 성공 이후에만 처리 위치 갱신, 공급자 장애의 노출은 데이터 신뢰를 위한 조건이다. 반면 확인 주기, 페이지 탐색 범위, 동시 요청 수, 복구 작업 주기와 재시도 대기는 실측과 공급자 조건에 맞춰 조정하는 운영 설정이다. 임의의 숫자를 금융 도메인의 정답이나 고정 성능 보장으로 취급하지 않는다.

| 항목 | 현재 동작 | 새 포털 경로의 결정 기준 |
| --- | --- | --- |
| 목록 확인 주기 | RSS는 30초 | 5~15초는 시험 후보다. 허용 요청 빈도, 응답 지연, 오류율을 확인하고 결정한다. 현재 값을 바꾼 상태는 아니다. |
| 목록 탐색 범위 | 공급자가 RSS에 포함한 유효 항목 전체 | 첫 페이지만 읽지 않고 이전 수집 경계까지 이어 읽는다. 제한에 걸려 경계까지 못 읽으면 수집 공백으로 기록하고 보충 작업으로 넘긴다. |
| 늦은 등록·순서 변경 | 포털 경로 미구현 | 최근 구간을 겹쳐 읽고 날짜별 목록과 대조한다. 시간만으로 종료하지 않고 이미 확인한 기사 식별자도 함께 사용한다. |
| 본문·모델 처리량 | 별도 작업자와 영속 분석 대기열 사용 | 공급자 요청 제한과 기기 자원, 가장 오래 기다린 기사와 최신 기사 지연을 보고 조정한다. 수집량을 줄여 추천 정확도가 높아진 것처럼 보이게 하지 않는다. |
| 정기 점검 주기 | Airflow 미연결 | 복구 가능한 원본 범위와 수집량을 기준으로 분·시간·일 단위 작업을 나눈다. 연결과 검증 전에는 임의의 정기 실행을 등록하지 않는다. |

## 실패 시 처리 계획

| 실패 상황 | 처리 원칙 | 복구 확인 |
| --- | --- | --- |
| 요청 시간 초과·일시적 서버 오류 | 요청별 제한 시간을 두고 마지막 성공 자료와 시각을 유지한다. 해당 수집원만 대기 시간을 늘려 재시도하고 다른 수집원은 계속 처리한다. | 마지막 성공 이후 공백 구간을 표시하고 원본 목록과 다시 대조한다. |
| 요청 과다·접근 거부 | 제공자가 안내한 재시도 시간을 존중하고 자동 요청을 줄이거나 중단한다. 우회·공격적 재요청으로 해결하지 않는다. | 허용 경로·사용 조건을 확인하고 필요하면 계약 피드 등 대안을 검토한다. |
| 페이지 구조 변경·파싱 오류 | 정상적인 기사 0건과 구분한다. 이전 보관 자료를 지우거나 오류 응답을 정상 수집으로 기록하지 않는다. | 수집 어댑터를 수정하고 저장된 예제와 실제 목록으로 재검증한 뒤 공백 구간을 보충한다. |
| 새 기사가 몰려 첫 페이지 밖으로 밀림 | 이전 경계까지 페이지를 이어 읽고, 부하 제한에 도달하면 미완료 구간을 남긴다. | 날짜별 목록이나 원본 보관 자료로 해당 구간의 기사 식별자를 대조한다. |
| 저장 실패·디스크 부족 | 저장 전에 처리 위치를 앞당기지 않는다. 화면에 보관 실패를 노출하고 재실행 시 같은 구간을 다시 읽는다. | 재수집 후 기사·버전·처리 위치가 함께 기록됐는지 확인한다. 원본에서 사라진 자료의 복구는 보장하지 않는다. |
| 작업자 종료·중복 실행 | 영속 처리 위치에서 재개하고 작업 권한·동일 기사 중복 방지를 적용한다. 최신 수집과 보충 작업의 중복 발견은 허용하되 중복 작업은 막는다. | 종료 전후의 기사 식별자, 처리 권한과 작업 건수를 대조한다. |
| 본문 접근 실패·유료 전문·LLM 실패 | 제목과 링크는 전체 기사에 남기고 본문·분석 상태를 표시한다. 실패한 요약을 정상 추천으로 올리지 않는다. | 재시도 후 원문 인용을 검증한다. 본문 확보 불가는 누락 없는 전문 수집으로 보고하지 않는다. |
| Airflow 중단 | 빠른 기사 발견은 상시 작업자로 계속 수행하고 정기 점검의 마지막 성공 시각과 밀린 구간을 남긴다. | 복구 후 빠진 구간을 재실행한다. 최신 목록만 재조회해서 과거 구간을 복구했다고 주장하지 않는다. |
| 지연이 계속 증가 | 수집·본문·분석 지연과 대기열 크기를 분리해 원인을 찾는다. 새 기사 발견을 느린 모델 호출 뒤에 묶지 않는다. | 실행 자원이나 구조를 조정하고 동일한 수집량에서 처리 지연·누락을 재측정한다. |

## 구현 순서와 수용 기준

먼저 포털 최신·날짜별 목록의 실제 데이터 경로와 페이지 이동, 식별자, 허용 범위를 확인한다. 현재 Npay 증권의 정적 HTML에는 기사 목록이 나타나지 않으므로 검증된 경로 없이 전수 수집을 구현 완료라고 선언하지 않는다. 이후 같은 저장 규칙을 사용하는 빠른 수집과 구간 보충 작업을 구현하고, 누적 보관 기사 조회를 추천과 별도로 연결한다. 실행 환경·의존성과 복구 작업을 검증한 다음 Airflow 일정을 연결한다.

수용 검증에는 새 기사 폭증, 늦게 등록된 기사, 같은 시각의 여러 기사, 중복 원문 링크, 수정·취소, 중간 페이지 실패, 재시작, 겹치는 수집과 보충, 저장 실패, 모델 미연결, 오래된 기사 페이지 조회를 포함한다. 전체 기사에서 추천 제외·미분석 자료와 동일 사건의 다른 원문이 빠지지 않는지 확인한다. 단위·통합 검증과 별도로 실제 목록과 일정 시간 대조한 발견 지연·미수집 식별자를 기록한다.

측정값은 수집원별 마지막 성공, 연속 실패, 마지막으로 완전히 대조한 구간, 미완료 복구 구간, 최초 발견까지의 지연, 본문·분석 완료 지연, 처리 대기와 중복 건수다. 발행·포털 제공 시각을 구분할 수 없는 경우 지연의 기준과 불확실성을 표시한다. 대조한 목록 밖의 기사까지 무누락을 검증했다고 주장하지 않는다.

## 선택을 다시 검토할 때

분 단위 도착이면 충분하고 반복 작업 관리 비용이 더 크다면 Airflow 단독 수집을 검토한다. 초 단위 지연을 요구하지만 포털 제공 자체가 느리거나 차단·구조 변경이 잦으면 공급 경로를 바꾸거나 계약 피드를 검토한다. 여러 수집 서버로 확장하면서 저장소 잠금과 작업 분배가 병목이면 별도 실행·저장 인프라를 검토한다. 각 변경에는 관찰한 문제, 대안, 선택 이유, 실패 대응과 검증 결과를 같은 결정 기록과 커밋 메시지에 남긴다.
