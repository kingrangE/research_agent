재실행할 때 출력 디렉터리는 아직 존재하지 않는 고유 경로로 바꾼다. `--snapshot /private/fixed-copy`를 주면 그 디렉터리의 `news.sqlite3`, `market.sqlite3`를 읽기 전용 연결로 백업하고 백업본의 지문을 남긴다. 이 옵션도 현재 제목과 저장된 가격만 재생하며 원본 본문, 원시 포털 응답, 기존 검수 결과를 재생하지 않는다. 원본을 직접 평가 대상으로 지정하지 말고 승인된 Linux 볼륨 사본을 사용한다. 현재 Worktree에는 그런 사본이 없어서 이 옵션은 실제 자료로 실행하지 않았다. 해당 옵션의 별도 cProfile 단계는 가격 사본을 전달하지 않아 현재는 자료 없음 경로만 프로파일한다. 실제 가격 경로를 프로파일하려면 그 단계에도 같은 가격 사본을 전달해야 한다.

실제 지원 경로는 `archive.store → event_facts.ingest/extract → data_worker.discover/enqueue/observe → event_reactions.load_inputs/calculate → data_worker.refresh_themes/theme_statistics.calculate → archive.browse/data_product.attach`다. 제목의 사건 분류와 당사자 연결은 `extract` 안에서 측정하며, 일반 뉴스 화면의 모든 종목 추천 경로나 원시 포털 파싱을 대표하지 않는다. `reaction_compute`는 관측 자료가 없는 분기 실행도 포함하므로 그 호출 횟수 자체가 가격 계산 성공 수는 아니다. 가격 결합의 DB 읽기와 결과 저장은 상위 `observe`에 포함된다. 테마의 독립 사건 수는 제품 자체에서 `independence_review_not_available`다.

기사 입력은 포털 파서로 생성한 합성 제목 10건이며 원시 파싱 실행은 측정 구간 밖이다. 3배와 10배에서는 ID, URL, 제목을 결정적으로 달리한다. 제목만 복제해 캐시 적중률을 늘리지는 않는다. 다만 같은 프로젝트 식별자를 보존하므로 독립 사건 수는 기사 수와 함께 늘지 않는다. 실제 본문 0건, 가격 0건, 전체 상장 목록 없음, 제품 지식의 등록 증권은 16개다. 확장 규모는 기사 입력 수에만 해당하며 독립 사건, 증권, 가격의 3배/10배 평가는 미검증이다. `timestamp_basis=portal_display`를 그대로 유지하여 공표 시각으로 잘못 간주하지 않는다.

신규는 사전 회차 후 뉴스와 파생 사실·작업 DB를 지우고 같은 입력을 새로 저장한다. 반복은 입력을 바꾸지 않고 대기 작업을 다시 관측하도록 한다. 정정은 앞의 10% 제목을 결정적으로 수정하고 새 버전과 최신 사건 제안의 원본 지문을 확인한다. 관계 변경은 관계 내용의 판정을 바꾸지 않고 관계 지문만 바꾸는 무효화 검사다. 실제 관계 의미 변경의 정확도 검사로 해석하지 않는다. 반복 조건은 원래 작업자의 4건 한도를 유지하며 새 pending 작업이 없으면 한 회차만 관측한다. 따라서 100건 전체의 관측 재계산을 끝냈다는 뜻이 아니며 재계산 수와 실제 관측 시도 분모를 JSONL에서 확인해야 한다. 기존 결과 대조는 같은 코드의 사전 회차 결과와의 분류·당사자·사건·원본 지문 비교이며 과거 운영 정답과의 대조가 아니다.

캐시 있음/없음은 작업자 SQLite 지문과 테마 지문 재사용 여부다. 이 경로에 별도 메모리 결과 캐시는 없으며 같은 Python 프로세스와 OS 페이지 캐시는 유지한다. 연관 종목 결과 재사용 정확도나 SQLite 파생 자료를 모두 제거한 상태의 비교는 미검증이다. 캐시가 적중해도 관측 불충족 결과를 재사용한 것일 수 있으므로 계산 성공과 분리한다.

각 조건은 사전 회차를 한 번 완전히 소진한 후 반복 3회다. 배수 3개 × 시나리오 4개 × 캐시 2개 × 반복 3개 × 계측 여부 2개로 구성한다. 계측 회차는 단조 `perf_counter`로 단계, 저장 완료부터 분류 시작, enqueue부터 observe 시작까지의 시간을 기록한다. 단계 시간은 하위 호출을 포함하므로 서로 더하지 않는다. 계측 없는 캐시 있음 회차는 작업자 내부의 단계 래퍼·SQL 추적·큐 계측을 제거한 원래 회차다. 전체 소진 시간에는 회차 사이의 상태 조회 비용이 포함되며 캐시 없음 회차에는 무효화 처치 비용도 포함된다. 별도 cProfile 실행은 반복 측정에 합치지 않는다. 퍼센타일은 정렬 후 ceil(p×n) 순위이며, 반복 3회의 p95/p99는 최댓값이므로 안정적인 꼬리 지연 추정으로 사용할 수 없다.

외부 대기 시간은 네트워크가 차단된 재생에서 측정할 수 없어 `null`이다. 큐 대기는 저장 완료→분류 시작과 작업 enqueue→관측 시작을 나눠 기록한다. 원래 수집부터 입수까지의 네트워크 지연은 없다고 가정하지 않는다. 예약된 관측 재시도를 앞당기는 것은 반복 시나리오의 명시적 처치이며 일반 도착 시각을 재현한 것이 아니다. 분석의 as-of와 저장 관측 시각은 실제 실행 시계이므로 시각을 고정한 과거 가격 재현 평가도 별도로 필요하다.

실행 주기의 기준은 현재 작업자의 회차 후 30초 sleep이며, 전체 반영 시간이나 정상 유입률 SLA가 정해져 있지는 않다. 측정 전에 잠정 단계 예산을 ingest 8초, discover 4초, observe 회차 합계 12초(최대 4건이므로 건당 3초), themes 4초, response 2초로 배분했다. 이 배분은 운영 승인을 받은 절대 SLA가 아니다. 회차 p95와 단계별 p95를 이 값과 비교하되 결과를 보고 예산을 바꾸지 않았다.

SQL 계측값은 사전 회차 이후의 조건 준비·검증 쿼리와 큐 관찰 쿼리까지 포함하는 하네스 총계다. 제품 단독의 최소 쿼리 수가 아니다. SQL 시간은 Connection.execute 호출에 한정되며 executescript, fetch 완료, commit/fsync 전체 시간은 포함하지 않는다. 쓰기 실행 시간은 INSERT/UPDATE/DELETE/REPLACE 호출 시간이며 잠금 대기가 섞일 수 있다. 잠금 오류 수는 기록하지만 독립 잠금 대기 시간과 운영 유사 DB 경쟁은 미검증이다. 최대 RSS는 전체 Python 프로세스 수명의 값이며 조건별 최대 메모리로 사용할 수 없다.

코드 경로와 프로파일에서 먼저 검토할 개선 후보는 매 회차 반복되는 사건 snapshot/당사자 결합과 SQLite 연결·스키마 준비 비용이다. 동일 입력의 사건 제안 읽기와 관계 검사를 회차 안에서 재사용하거나 실제 쿼리 계획에 맞춘 인덱스를 검토할 수 있다. 아직 제품 코드를 최적화하지 않았으며 의미 보존 검사를 유지한 같은 입력 전후 비교가 필요하다. 가격과 전체 상장 목록이 없으므로 실제 가격 결합·테마 쌍별 계산이 가장 큰 병목인지 판단할 수 없다.

별도로 운영 스케줄의 한계가 있다. 현재 회차는 최대 4개 작업 후 30초를 쉬므로 계산 비용이 0이어도 약 0.133 작업/초가 상한이고 실제 회차 주기는 30초+가공 시간이다. 이 합성 입력처럼 기사당 public/available 2개 작업이 생기면 약 0.067 기사/초 이하가 된다. 100기사의 200개 작업을 50회차로 처리하려면 첫 회차를 즉시 시작하더라도 회차 사이 휴지만 최소 49×30=1470초다. 위 연속 재생의 수초 소진 시간과 구분해야 한다. 재시도나 추가 유입은 이 하한을 더 늘린다. 실제 유입 추적이 없으므로 적체가 장기적으로 증가하지 않는지는 미검증이다.

완료 기준별로 외부/큐/계산 분리 도구와 합성 경로 프로파일은 부분 제출, 실제 현재·3배·10배 전체 규모 결과는 미검증, 중복·정정의 로컬 의미 보존 검사는 통과하되 운영 기존 정답 대조는 미검증, 국소 병목·스케줄 한계와 잠정 예산 판정은 제출 상태다. 후속 검증에는 고정된 실제 Linux DB 사본과 전체 상장 목록·관계 규칙, 본문/가격/독립 사건을 함께 확장하는 입력, 정상 유입 도착 추적, 운영 유사 다중 DB 작업자, 독립 잠금 대기 계측, 사람 검수 결과 및 실제 관계 변경이 필요하다. 이 자료를 확보하기 전 이슈를 최종 완료하거나 운영 성능 목표 통과로 표시해서는 안 된다.

2026-11-17 후속 작업에서 합성 본문·가격·거래일을 보충하여 지원 성공 경로를 측정했다. [추가 성공 경로 평가](issue26-supported-processing.md)를 함께 확인한다. 이 문서의 원래 대기·미지원 수치는 변경하지 않았다.
후속 버전은 별도 프로파일 단계에도 같은 시장 DB 사본을 전달하므로 위에서 기록한 당시 프로파일 입력 누락 제한은 해소했다. 실제 DB 사본 모드의 검증 부재는 유지한다.
