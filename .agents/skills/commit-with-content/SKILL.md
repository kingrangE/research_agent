# 맥락을 남기는 커밋

## 목표와 기본 원칙

- 프로젝트를 처음 보는 개발자가 변경의 필요성, 바뀐 동작, 판단 근거, 실패 처리, 확인한 범위를 이해하게 작성하라.
- 실제 변경과 확인 가능한 근거에서 내용을 구성하라. 설계 의도와 구현 상태, 검증 결과를 구분하라.
- 비즈니스 규칙은 대상, 조건, 행동, 결과로 설명하라. 기술적 구현은 해당 동작을 성립시키는 메커니즘과 적용 경계를 설명하라.
- 기본 언어는 한국어로 하라. 현재 사용자의 명시적인 언어 요청과 저장소의 필수 형식을 반영하라.
- 제목과 구획명을 제외한 본문은 `- ` 불릿으로 작성하라. 중간점 문자 U+00B7은 사용하지 말라.
- 내용과 문체가 헷갈리면 이 문서의 7번 작성 예시를 참고하라. 예시의 가상 사실을 실제 변경에 복사하지 말라.

## 1. 변경 범위와 근거 확인

- 요청을 메시지 초안 작성, 기존 메시지 개선, 실제 커밋 중 하나로 구분하라. 메시지 작성 요청은 커밋 실행 요청으로 확대하지 말라.
- 실제 저장소에 접근할 수 있으면 다음 자료를 필요한 범위에서 확인하라.
  - 적용되는 사용자 지시, `AGENTS.md`, 기여 가이드, 커밋 템플릿.
  - 현재 브랜치, `git status --short`, staged diff, unstaged diff, 관련 신규 파일의 내용.
  - 최근 커밋 제목 5~10개에 나타난 형식과 언어. 관행을 필수 규칙으로 단정하지 말라.
  - 관련 요구사항, 승인된 설계 결정, 변경 전후 코드, 기존 테스트 결과와 실행 로그.
- 사용자가 제공한 diff만 있으면 그 범위에서 작성하고, 저장소 전체나 실행 결과를 확인했다고 말하지 말라.
- 메시지 대상이 staged 변경인지 전체 변경인지 확인하라. 서로 다른 목적의 변경이 섞여 있으면 먼저 의미 단위를 나누어라.
- 근거가 충돌하면 실제 diff와 실행 결과로 현재 동작을 확인하라. 오래된 설계 문서를 구현 완료의 증거로 사용하지 말라.
- diff만으로 과거의 대안 검토나 선택 의도를 알 수 없으면 추측하지 말라. 중요한 빈칸은 `선택 근거 미확인`처럼 짧게 표시하고, 커밋 범위를 결정할 수 없는 경우에만 필요한 질문을 하라.

## 2. 커밋 단위 정하기

- 하나의 커밋이 하나의 변경 목적을 설명하고 검토할 수 있도록 묶어라.
- 하나의 동작을 완성하는 구현, 관련 테스트, 필요한 문서는 함께 묶어라. 파일 종류만으로 기계적으로 나누지 말라.
- 독립적인 기능 추가, 버그 수정, 정리 작업이 섞여 있으면 분리하라. 실행 가능성이나 검증 가능성을 깨는 분리는 피하라.
- 사용자가 지정한 범위와 기존에 staged된 변경을 보존하라. 다른 사람이나 다른 작업의 변경을 포함하거나 되돌리지 말라.
- 사용자가 메시지만 요청하면 필요한 커밋 분리안과 각 메시지를 제시하라. 인덱스를 변경하지 말라.

## 3. 처음 읽는 사람을 위한 표현

### 비즈니스 규칙

- 필요한 배경을 한 문장으로 먼저 제공하라. 예: `사용자가 같은 신청을 다시 보내도 처리 결과는 한 건으로 유지해야 한다.`
- 변경 전의 문제와 변경 후의 결과를 대상, 조건, 동작이 드러나는 문장으로 설명하라.
- 함수명, 변수명, 클래스명, 내부 상태 코드와 테이블명을 역할과 의미를 설명하는 말로 바꾸어라.
- `중복 처리 개선`, `로직 수정`, `예외 처리 강화`처럼 실제 동작을 알 수 없는 표현을 구체화하라.
- 기존 정책과 새로 바뀐 정책을 구분하라. 기술적 수정을 새 비즈니스 정책 도입처럼 표현하지 말라.
- 사용자에게 보이는 실패, 재시도 가능 여부, 기존 데이터 보존, 운영자가 해야 할 조치를 해당되는 경우 설명하라.

### 기술적 구현

- 기술 이름에 이어 어떤 방식으로 문제를 해결하며 어디까지 적용되는지 설명하라.
- 트랜잭션의 시작과 확정 경계, 유일성 제약의 기준, 잠금 대상, 작업 점유 방식, 재시도 조건, 타임아웃, 캐시 무효화 기준 등 변경을 이해하는 데 필요한 세부 사항을 써라.
- SQL 키워드, HTTP 상태 코드, 프로토콜, 라이브러리, 자료구조, 알고리즘, 인덱스, 격리 수준은 정확하게 표기하라. 익숙하지 않은 용어는 첫 등장에 역할을 짧게 설명하라.
- 내부 함수명, 변수명, 테이블명과 컬럼명은 기술적 구현 구획에서도 의미로 풀어 써라. SQL은 `UNIQUE 제약`, `ON CONFLICT ... DO NOTHING`처럼 필요한 문법을 제시하고, 제약의 대상은 `직원과 교육 과정의 조합`처럼 설명하라.
- 정확한 표기가 필요한 공개 API 경로, 외부 설정 키, 오류 코드, 재현 명령은 기술적 구현이나 검증 항목에서 역할 설명과 함께 최소로 인용하라. 이 예외를 내부 식별자나 전체 SQL을 나열하는 근거로 쓰지 말라.
- `트랜잭션으로 처리`라고만 쓰지 말고 함께 확정되는 데이터와 범위 밖의 외부 작업을 구분하라.
- `멱등성 보장`이라고만 쓰지 말고 같은 요청을 판단하는 기준, 반복 요청의 결과, 적용 범위를 설명하라.
- 성능이나 안정성을 개선했다고 주장할 때는 측정 조건과 결과를 근거로 하라. 실측하지 않았다면 구현 변경까지만 설명하라.

### 불릿과 문장

- 한 불릿에는 한 가지 핵심 사실을 담아라. 원인과 결과처럼 함께 읽어야 하는 관계는 한 문장으로 연결하라.
- 하위 불릿은 한 단계까지만 사용하라. 긴 문단, 표, 코드 덩어리는 커밋 본문에서 피하라.
- 구획당 1~3개 불릿을 기본으로 하되, 필요한 근거를 생략하거나 불릿 수를 맞추려고 내용을 만들지 말라.
- 구체적인 동사를 사용하라. `고도화`, `최적화`, `견고하게 개선`만으로 결과를 설명하지 말라.
- 같은 사실을 여러 구획에서 반복하지 말라. 정책은 변경 내용에, 구현 메커니즘은 기술적 구현에, 실행한 확인은 검증에 적어라.
- 자료에 언급되었다는 이유만으로 무관한 기능이나 변경하지 않은 항목을 나열하지 말라. 독자가 실제 영향이나 보장 범위를 오해할 수 있는 한계만 포함하라.

## 4. 제목과 본문 작성

### 제목

- 무엇이 달라지는지 드러나는 한 줄로 작성하라. 배경과 세부 근거는 본문으로 옮겨라.
- 저장소가 커밋 타입, scope, 이슈 번호, 길이 제한을 요구하면 그대로 따르라.
- 별도 형식이 없으면 `중복 신청을 한 건으로 처리하도록 수정`처럼 한국어로 변경 결과를 쓰라. Conventional Commits 형식을 임의로 의무화하지 말라.
- `수정`, `업데이트`, `작업 완료` 같은 단독 제목과 파일명 나열을 피하라.

### 실질적인 구현 변경의 기본 구조

```text
변경 결과를 드러내는 제목

[문제]
- 어떤 상황에서 누구에게 어떤 문제가 발생했는지 설명한다.

[변경 내용]
- 대상과 조건을 포함해 변경 후의 비즈니스 동작을 설명한다.

[대안과 선택 이유]
- 실제 검토한 대안과 채택하지 않은 이유를 적는다.
- 선택한 방식이 현재 요구와 제약에 맞는 이유를 적는다.

[기술적 구현]
- 핵심 메커니즘, 적용 범위, 필요한 구체적인 기술 정보를 적는다.

[실패 대응]
- 실패를 어떻게 감지하고 어떤 상태를 보존하며 어떻게 복구하는지 적는다.
- 적용 범위 밖의 실패나 아직 남은 한계가 있으면 적는다.

[검증]
- 실제 실행한 확인, 실행 조건, 관찰한 결과를 적는다.
- 실행하지 못한 중요한 확인과 그 이유가 있으면 적는다.
```

- 매번 문제, 대안, 선택 이유, 실패 대응, 검증 결과의 다섯 관점을 확인하라. 위 구조는 읽기 쉽게 변경 동작과 기술 구현을 추가로 구분한 것이다.
- 대안과 선택 이유는 현재 기록에 근거하라. 당시 비교한 적 없는 접근을 과거에 검토한 것처럼 만들지 말라.
- 실질적인 변경인데 대안 기록이 없으면 해당 구획에 `별도 대안 비교 기록 없음` 또는 확인된 선택 근거만 적어라.
- 단순 오탈자, 문서 정리, 형식 수정은 문제, 변경 내용, 검증 중심으로 줄여라. 무관한 기술적 구현이나 실패 대응 구획을 억지로 채우지 말라.
- 숫자, 테스트 개수, 응답 시간, 재시도 횟수, 기존 장애의 발생 사실을 만들어내지 말라.
- 실패 대응이 아직 없다면 미구현이라고 명시하라. 향후 계획은 구현 완료와 분리하라.
- 검증은 `실행해 통과`, `실행해 실패`, `정적 확인`, `미실행`을 구분하라. 테스트 파일의 존재를 실행 성공으로 표현하지 말라.
- 관련 결정 기록이 있으면 커밋과 일치하는지 대조하라. 문서 갱신은 요청 범위나 저장소 규칙에 포함될 때 수행하라.

## 5. 요청된 경우 커밋 실행

- 현재 요청과 앞선 대화에서 승인된 범위에 따라 진행하라. 이미 요청받은 일반적인 로컬 커밋을 위해 같은 확인을 반복하지 말라.
- 해당 변경에 필요한 검증과 저장소의 필수 검사를 수행하라. 이미 유효한 실행 결과는 재사용하고, 작은 수정 때문에 무관한 테스트를 새로 만들거나 전체 검사를 반복하지 말라.
- 필수 검사 실패를 우회하거나 Git hook을 끄지 말라. 수정 가능한 문제는 요청 범위에서 해결하고, 남은 실패나 실행 제약을 정확히 보고하라.
- 커밋 직전에 상태와 staged diff를 다시 확인하라. 선택한 파일이나 변경 조각만 stage하고, 관계없는 staged 변경까지 포함하지 말라.
- 기존 인덱스 상태나 다른 작업을 보존하면서 범위를 분리할 수 없으면 중단하고 필요한 범위만 확인하라.
- 메시지는 UTF-8 임시 파일에 정확한 줄바꿈으로 기록하고 `git commit -F`로 전달하라. 셸 인용이나 명령 치환으로 본문이 달라지지 않게 하라.
- 커밋 후 생성된 해시, 실제 저장된 메시지, 포함된 변경과 남아 있는 작업 상태를 확인하라.
- push, PR 생성, 병합, amend와 기존 이력 재작성은 각각의 요청이나 기존 위임 범위가 있을 때만 수행하라.
- 커밋이 생성되지 않았거나 검사에서 멈췄으면 완료로 보고하지 말라. 재시도 전 현재 상태를 확인해 중복 커밋을 피하라.

## 6. 최종 확인과 응답

- 프로젝트를 모르는 사람이 문제와 바뀐 규칙을 이해할 수 있는지 읽어보라.
- 함수명과 변수명을 의미 설명으로 바꾸었는지, 중요한 기술 메커니즘이 구체적으로 남아 있는지 확인하라.
- 검토하지 않은 대안, 추정한 의도, 실행하지 않은 테스트, 측정하지 않은 성능이 사실처럼 들어가지 않았는지 확인하라.
- 메시지의 모든 주장과 실제 커밋 범위가 일치하는지 확인하라.
- 초안 요청에는 바로 사용할 수 있는 메시지를 코드 블록으로 제시하라. 필요한 불확실성 설명은 메시지 밖에 짧게 붙여라.
- 실제 커밋 요청에는 커밋 해시와 제목, 핵심 변경, 검증 결과, 남은 제한을 불릿으로 보고하라.

## 7. 작성 예시

- 아래 사례는 작성 방식을 보여주는 가상 예시다. 숫자, 검증 결과, 설계 의도를 실제 작업에 그대로 복사하지 말라.
- 각 작업의 요구사항, diff, 설계 기록, 실행 결과에 맞춰 작성하라.

### 7.1. 비즈니스 규칙과 기술적 구현 구분

#### 피할 표현

- `process_article()에서 last_seen_id를 갱신한 뒤 save_article()을 호출하던 순서를 변경했다.`
- `is_recommended가 false여도 get_all_items()에서 반환하도록 수정했다.`
- `try-except를 추가해 안정성을 개선했다.`

#### 사용할 표현

- 문제: 기사 저장이 실패해도 수집 위치가 먼저 앞으로 이동해, 재시작할 때 저장하지 못한 기사를 건너뛸 수 있었다.
- 변경 동작: 기사 저장이 완료된 범위까지만 수집을 마친 것으로 처리하고, 실패한 구간은 다시 수집한다.
- 비즈니스 규칙: 추천 대상으로 선정되지 않은 기사도 전체 기사 목록에서는 조회할 수 있다.
- 기술적 구현: SQLite 트랜잭션 하나에서 기사와 처리 위치를 함께 저장하고, 쓰기 실패 시 두 변경을 모두 롤백한다.
- 실패 대응: 저장 오류는 정상 수집과 구분해 표시하고, 이전에 저장한 기사와 마지막 성공 위치를 유지한다.
- 구체적인 검증: 두 번째 쓰기를 실패시키는 테스트에서 기사와 처리 위치가 모두 이전 상태로 남는지 확인했다. 실제 통과 로그가 있을 때만 이렇게 적는다.

### 7.2. 설계 근거가 있는 변경의 전체 예시

- 전제: 다음 동작이 실제 diff에 포함되고, 대안 비교가 기록되어 있으며, 명시한 검증을 실제 실행한 상황에서만 이 수준으로 작성하라.
- 전제: 기사 중복 기준은 제공처와 원문 식별자의 조합이고, 외부 분석 요청은 별도 작업이다.

```text
기사 저장 실패 후 재시작할 때 수집 내용이 누락되는 문제 수정

[문제]
- 뉴스 수집기는 저장한 기사와 마지막 수집 위치를 사용해 중단 이후의 작업을 이어간다.
- 기사를 저장하기 전에 처리 위치를 갱신해, 저장 실패 후 재시작하면 미저장 기사를 건너뛸 수 있었다.

[변경 내용]
- 기사 저장까지 완료된 구간만 처리한 것으로 기록한다.
- 같은 제공처의 동일 기사를 다시 수집해도 보관 건수가 늘어나지 않게 한다.

[대안과 선택 이유]
- 두 저장 작업의 호출 순서만 바꾸는 방법은 중간 종료 시 하나만 반영되는 문제를 남긴다.
- 기사와 처리 위치를 함께 확정하는 트랜잭션을 선택해, 두 기록이 서로 어긋나는 구간을 없앤다.

[기술적 구현]
- SQLite 트랜잭션 하나에서 기사 저장과 처리 위치 갱신을 함께 확정한다.
- 제공처와 원문 식별자의 조합에 UNIQUE 제약을 적용하고, 충돌 시 기존 기사를 유지한다.
- 기사 본문을 분석하는 외부 요청은 이 트랜잭션 범위에 포함하지 않는다.

[실패 대응]
- 저장 오류가 발생하면 기사와 처리 위치 변경을 함께 롤백하고 마지막 성공 위치를 유지한다.
- 재시작하면 실패한 구간부터 다시 읽는다. 제공처에서 이미 삭제한 기사까지 복구할 수는 없다.

[검증]
- 저장 성공 후 기사와 처리 위치가 함께 반영되는 테스트를 실행해 통과했다.
- 중간 쓰기 실패 시 두 기록이 모두 이전 상태를 유지하고, 같은 구간을 재처리해도 중복되지 않는 테스트를 실행해 통과했다.
- 실제 제공처의 과거 기사 조회와 운영 환경의 디스크 부족 상황은 검증하지 않았다.
```

### 7.3. 대안이나 검증 근거가 부족할 때

- diff에는 변경 동작이 있지만 과거 설계 논의나 테스트 실행 결과가 제공되지 않은 상황을 가정하라.
- 현재 선택의 가능한 장점을 당시 의도로 둔갑시키지 말라.

```text
추천 여부와 관계없이 전체 기사 목록을 조회하도록 수정

[문제]
- 전체 기사 목록에도 추천 결과를 거르는 조건이 적용되어 추천되지 않은 기사를 찾아볼 수 없었다.

[변경 내용]
- 전체 기사 목록에는 보관된 기사를 추천 여부와 관계없이 포함한다.
- 추천 화면의 선정 조건은 유지한다.

[대안과 선택 이유]
- 별도 대안 비교 기록 없음.

[기술적 구현]
- 전체 기사 조회에서만 추천 여부를 제한하는 필터를 제거한다.
- 최신순 정렬과 페이지 크기 제한은 유지한다.

[실패 대응]
- 이 변경에는 조회 실패 시 재시도나 대체 결과 제공을 추가하지 않았다.

[검증]
- 정적 확인: 제공된 diff에서 전체 기사 조회의 필터만 제거된 것을 확인했다.
- 미실행: 테스트 실행 결과가 제공되지 않아 실제 조회 동작은 확인하지 못했다.
```

### 7.4. 작은 변경은 짧게 작성

- 설치 안내의 명령어 오탈자만 수정했고 실행 환경은 없는 상황을 가정하라.
- 관련 없는 대안, 장애 복구, 성능 개선 이야기를 덧붙이지 말라.

```text
개발 환경 설치 안내의 잘못된 의존성 파일 경로 수정

[문제]
- 안내된 설치 명령이 존재하지 않는 의존성 파일을 가리켰다.

[변경 내용]
- 설치 명령에서 실제 저장소에 있는 의존성 파일을 사용하도록 경로를 바로잡았다.

[검증]
- 정적 확인: 안내한 경로에 파일이 존재하고 수정 범위가 문서 한 곳인 것을 확인했다.
- 미실행: 의존성 설치 명령은 실행하지 않았다.
```
