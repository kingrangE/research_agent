# #27 활성 세션 부하 평가 v1

기준 구현은 `f7b9190c5bba1166cba2166d4361f2cb0712ed86`이다. `scripts/load_active_sessions.js`는 k6 HTTP 발생기이며 렌더링 브라우저가 아니다. `scripts/plan_active_sessions.py`는 네트워크 없이 환경과 사전 예산을 기록한다. 제품 서버, 인증, 원본 볼륨, 수집 작업자에는 변경이 없다. 이 디렉터리는 저장소 평가 코드의 재현 절차이며 원시 데이터는 `.data/validation/issue27/` 등 비공개 경로에 둔다.

## 고정 조건과 실행 자원

본 실행 전 발생기와 대상 서버를 다른 전용 호스트에 마련한다. 유료 자원을 새로 구매하거나 운영 서버에 실행할 권한은 이 절차에 포함되지 않는다. 공유 Mac에서 다른 평가 작업과 함께 얻은 수치는 격리 성능으로 해석하지 않는다. 최소 구성은 발생기 1대, 대상 서버와 DB·기존 쓰기 작업자 1대, 소수 실제 브라우저이며 CPU·RAM의 충분한 크기는 아직 측정하지 못했다. 10,000 VU에 대한 k6 메모리와 열린 연결 상한을 100→1,000 단계에서 실측한 뒤 증설 필요를 판단한다. 총 세션 유지 시간은 100·1,000·5,000명 각 10분, 10,000명 30분과 별도 2시간으로 최소 3시간이다. 여기에 낮은 기준선, 요청 집중·캐시·장애·복구·도착률 시험 시간이 추가된다. 비용은 제공 자원과 응답 크기가 없어 미산정이며 구매는 하지 않았다.

사전 예산은 정상 구간 API별 p95 ≤1,000ms, p99 ≤3,000ms, 시도한 요청 중 실패 ≤0.1%, 장애 제거 후 정상 복귀 ≤60초, 기사·정정 소실/잘못된 종목/정상값 위장 0건이다. 실행 뒤 변경하지 않는다. 장애 구간과 복구 구간은 정상 지연 예산과 분리한다. LLM·임베딩은 0회로 고정한다.

DB는 원본 Linux 볼륨에서 일관된 SQLite backup으로 복사해 격리 볼륨에 놓고 원본을 마운트하지 않는다. DB별 스키마·테이블 행 수, 기사/정정 ID와 내용의 지문, 가격·상장 전체 목록·관계 규칙의 수와 지문, 작업 키별 상태/재시도/완료/중복 수를 비공개 기준 파일에 저장한다. 사본에서만 쓰기를 병행하고 변경이 예정된 테이블은 입력 회차와 예상 변경을 별도로 기록한다. 읽기 전용 불변 파일 지문만 비교해서 정상 쓰기를 손상으로 판정하지 않는다. 복구 후 기사·정정과 작업 키를 기준 파일·고정 입력에서 독립 대조한다. 아직 이 자료나 전체 목록을 확보하지 못했다.

외부 제공처는 격리 네트워크의 기록 응답 서버로 교체하고 지연·429·5xx·시간 초과·누락 가격을 재생한다. 실제 토스 인증과 LLM·임베딩 자격 증명을 대상에 넣지 않는다. OS/네트워크 수준에서 외부 egress를 차단하고 차단 로그·모의 제공처 호출 수도 기록한다. manifest의 선언만으로 차단을 검증했다고 보고하지 않는다. 이 발생기는 대상을 시작하거나 제공처·DB·장애를 제어하지 않는다.

## 임시 요청 혼합과 예상 분모

`web/app.js`의 `load`, `loadArchive`, `loadMarket`, `loadQuotes`, `loadTimeline` 및 맨 아래 5초 타이머를 확인했다. 모든 세션은 5초마다 dashboard, 60%는 market-watch, 25%는 검색/필터/페이지별 articles, 15%는 stock-timeline을 요청한다. 시세 캐시의 10초 조건은 두 tick마다 quotes로 표현한다. 종목 그룹은 30초마다 뉴스 상세로 이동하는 조건부 detail 요청을 추가한다. 그룹은 VU ID의 100 단위로 고정하고 seed 27로 요청 fixture와 첫 폴링 시각을 분산한다. `SYNC=1`은 첫 시각을 집중시키고 `POPULAR=1`은 시세·차트 fixture를 첫 종목에 집중한다. 검색어·테마·페이지 cursor·종목은 실제 사본에 유효한 fixture를 여러 개 준비한다. 생각 시간·상세 모달 체류·시세 오류시 5초 재조회와 추가 클릭 요청은 아직 브라우저 보정 전 가정이다. 본 v1의 조건부 요청은 완전한 화면 재현으로 주장하지 않는다.

| 정상 구간 | 예상 tick | 예상 HTTP 요청 | 예상 RPS |
| --- | ---: | ---: | ---: |
| 100명 10분 | 12,000 | 30,300 | 50.5 |
| 1,000명 10분 | 120,000 | 303,000 | 505 |
| 5,000명 10분 | 600,000 | 1,515,000 | 2,525 |
| 10,000명 30분 | 3,600,000 | 9,090,000 | 5,050 |
| 10,000명 2시간 | 14,400,000 | 36,360,000 | 5,050 |

10,000명 기준 경로별 예상 RPS는 dashboard 2,000, market 1,200, feed 500, timeline 300, quotes 1,000, detail 50이다. 평균 응답 크기를 B bytes로 실측하면 payload 하한은 `5050 × B bytes/s`이며 TLS·헤더·재시도와 브라우저 트래픽을 더해야 한다. 실제 브라우저에서 홈/검색·페이지/종목·차트·뉴스 모달의 최소 한 순환과 정상/오류 시 캐시 조건을 네트워크 추적으로 수집한다. 개인정보·원문·가격을 제거한 경로/시각/조건 추적과 원본의 비공개 지문을 보존하고 이 가정을 보정한 뒤 버전을 올려 기대 RPS를 다시 사전 고정한다. 추적이 없으면 화면 빈도와 생각 시간 보정은 미검증이다.

## 비공개 manifest와 내용 검증

manifest는 `base_url`(끝 slash 없는 격리 origin), `isolated: true`, `external_egress_blocked: true`, `product_mode: "data"`, `browser_trace_calibrated: false` 및 `dashboard`, `market`, `feed`, `quotes`, `timeline`, `detail` 배열을 가진다. 각 배열 원소는 `{ "path": "/api/...?...", "assertions": [{ "pointer": "/필드/하위필드", "equals": "고정 기대값" }] }` 형식이다. JSON pointer의 `~0`, `~1`을 지원하며 equals는 문자열·숫자·불리언·null이다. 실제 종목·ID·가격 정답은 manifest에만 넣고 커밋하지 않는다. 상대 API 경로만 허용하고 HTTP redirect를 따라가지 않는다. 대상의 격리는 운영자가 별도로 확인해야 한다.

dashboard는 data 모드, 기사 수와 대표 ID, market은 시장·추적 수·종목 코드, articles는 필터/페이지별 정확한 ID·수, quotes는 요청한 코드별 코드·상태·가격·기준 시각, timeline은 해당 종목·점 수·시각, detail은 해당 기사 ID·관련 종목·누락 상태를 확인한다. 필요한 수의 scalar assertion을 넣는다. 경로별 실제 응답 스키마를 기준으로 작성하고 가상의 필드 이름을 사용하지 않는다. 입력을 고정할 수 없는 시각 필드는 assert 대상에서 제외하되 독립 최신성 검사와 연결한다. 장애별 기대 상태가 달라지면 별도 manifest와 지문을 사용한다. 가격 누락은 null/명시적 missing 또는 error 상태로 확인하며 정상 가격으로 채우지 않는다. 2xx라도 JSON 파싱·assertion 실패는 실패다. 4xx/5xx/timeout/연결 오류는 성공으로 허용하지 않는다. 이 검사는 선택된 필드만 검사하므로 전체 무결성 대조를 대신하지 않는다.

## 재현 명령

Node 23.10.0, Python 3.13.2로 계약 검사를 실행했다. 발생기는 k6 0.54 이상을 대상으로 작성했으나 현재 호스트에는 k6가 없어 네이티브 호환성을 실행 검증하지 못했다. 실제 실행에는 설치된 정확한 k6 버전·바이너리 지문을 사전에 기록한다. 아래 값은 자원·사본·manifest·추적을 마련한 뒤 격리 호스트에서만 채운다. 각 회차에는 새 출력 디렉터리를 사용한다.

```sh
node --test tests/test_active_sessions.mjs
python3 -m unittest discover -s tests -p test_active_sessions_plan.py
TZ=Asia/Seoul python3 scripts/plan_active_sessions.py --output .data/validation/issue27/run-unique/preflight.json --input /private/snapshot/news.sqlite3 --input /private/snapshot/full-catalogue.json --input /private/manifest.json
```

```sh
MANIFEST=/private/manifest.json MANIFEST_SHA256=RECORDED_SHA256 USERS=100 DURATION=10m MODE=sessions SEED=27 SUMMARY=/private/issue27-unique/summary.json k6 run --out json=/private/issue27-unique/metrics.json scripts/load_active_sessions.js
```

동일 프로세스를 계속 증가시키는 ramp 대신 각 단계별 별도 고정 VU 회차를 실행한다. 위 명령의 USERS/DURATION만 1000/10m, 5000/10m, 10000/30m, 10000/2h로 변경하고 각 출력 디렉터리를 분리한다. 더 낮은 기준선은 동일 100 VU 단계 전에 별도 작은 실제 브라우저/기존 소규모 벤치마크로 측정하고 10,000명 판정에 합산하지 않는다. 각 단계 종료시 자원/실패율을 검토해 안전 한도를 넘으면 그 지점에서 중단하고 최고 유지 부하를 보고한다. 캐시를 재시작한 경우 그 사실을 구분하여 기록한다. 10분 미만 유지한 세션 수는 최고 10분 유지 부하로 기록하지 않는다.

같은 설정으로 `MODE=arrival` 시험을 별도로 실행한다. 이때 세션 tick 도착률은 `USERS/5초`, 기대 HTTP RPS는 같은 혼합이다. arrival iteration은 독립 요청 묶음이며 지속 세션으로 세지 않는다. `GENERATOR_VUS`는 사전 예산에 맞게 고정하며 무한 확장하지 않는다. 실행 지연이 요청 생성을 감소시키면 native `dropped_iterations`, 실제 tick·시도 수, 미실행 기대 수로 드러내고 서버 통과로 판정하지 않는다. k6 batch 내 경로별 연결 제한·발생기 CPU가 도착률에 영향을 줄 수 있다.

정상에서 `SYNC=0/1`, `POPULAR=0/1` 및 warm/재시작·무효화 캐시를 별도 회차로 비교한다. warm은 명시적 예열 후, restart는 격리 서버만 재시작한 후 시작하고 OS 캐시까지 cold라고 부르지 않는다. `SYNC=1`은 constant-vus 시험에만 적용되며 arrival executor의 균등 도착을 집중 요청 시험으로 부르지 않는다.

## 계측·장애·복구·판정

두 호스트에서 UTC/NTP offset을 확인하고 정상 실행 전후 오차와 시간대를 기록한다. 1초 간격으로 프로세스/호스트 CPU, RSS·swap, 네트워크 송수신, 디스크 I/O, FD·연결·스레드, DB lock 대기, 쓰기 작업자의 적체/가장 오래된 작업/재시도/완료/중복을 수집한다. Linux라면 `pidstat -rudw -p PID 1`, `sar -n DEV,TCP,ETCP 1`, `iostat -xz 1`, `ss -s`, `/proc/PID/fd`와 대상 로그를 비공개로 보존한다. 도구가 없는 지표는 미측정으로 남긴다. DB lock 대기는 SQLite busy 로그와 계측이 없으면 미검증이며 HTTP 지연을 DB 대기라고 추정하지 않는다. 명령 출력에 원문·가격·인증이 포함되면 집계만 공개한다. 발생기 CPU/메모리/네트워크/연결 한계와 dropped iteration, 서버 CPU/메모리, DB busy, 모의 외부 지연을 시간축으로 대조해 원인을 분리한다.

원시 k6 JSON은 요청 하나당 여러 metric row를 기록한다. 30분에 약 909만 요청, 2시간에 약 3,636만 요청이므로 100명 사전 실행에서 요청당 출력 bytes를 측정하고 전체 출력 예산과 보존 공간을 먼저 확보한다. 출력 공간 부족이나 계측 I/O로 부하 발생이 밀리면 발생기 한계로 보고한다. fixture의 요청 본문·시세는 metric에 기록하지 않고 기본 system tag의 URL도 제외한다. k6 자체 오류 로그에는 URL이 남을 수 있으므로 모든 로그는 비공개로 취급한다.

소수 실제 브라우저는 별도 프로세스로 유지하며 탭 visibility, 네트워크 요청, 화면에 데이터가 보이기까지의 지연, 실패 문구·복구, 모달·차트 표시를 동일 시간축에서 기록한다. HAR에 실제 원문/시세/쿠키를 공개하지 않는다. VU 수와 렌더링 브라우저 수를 각각 보고한다.

장애 자동화는 제공하지 않는다. 격리 환경의 소유자가 아래 장애를 하나씩 주입·제거하고 시작/제거 시각, 범위, 명령, exit code를 원시 기록에 남긴다. 운영 컨테이너·인증·원본 볼륨에 실행하지 않는다. 부하 유지와 감소 후를 별도 시험하며 정상→fault→recovery 전체의 동일 HTTP 부하는 계속 유지한다. 현재 스크립트의 `PHASE`는 회차 전체에 고정되므로 이 전체 회차를 `PHASE=fault`로 실행하고 원시 metric timestamp를 장애 타임라인으로 잘라 정상/장애/복구 예산을 각각 적용한다. 회차를 중간 종료해 새로 실행하면 연속 유지·복구 증거가 되지 않는다.

| 장애 | 주입 대상·독립 확인 |
| --- | --- |
| 서버·작업자 재시작 | 격리 프로세스만 종료/재시작, PID·ready·작업 키 재개·중복/소실 확인 |
| 외부 429·5xx·timeout | 기록 응답 프록시의 오류 스케줄, 요청 수·backoff·오류 상태 확인 |
| DB 쓰기 잠금·짧은 실패 | 복사본의 제한시간 transaction/격리 fault adapter, 해제 시각·busy·대기 작업 확인 |
| 일부 가격 누락 | 고정 코드의 명시적 누락, 이전 값/미확인 표기와 정상값 위장 0건 확인 |

복구는 장애 제거 시점부터 모든 주요 API가 사전 정상 예산과 올바른 내용으로 돌아오고 작업 적체가 정상 배경 쓰기 수준에 도달한 최초 시각으로 정의한다. 처음 성공한 HTTP 200 하나로 복귀했다고 보지 않는다. 최소 연속 60초 정상 확인 구간을 유지하고 그 시작 시각으로 복귀 시간을 계산한다. 복구 관찰 종료까지 복귀하지 않으면 censored/미달로 보고한다. DB의 저장 기사·정정·작업 키 대조가 없으면 무결성은 미검증이다.

기본 요약은 항상 `goal_10000=unverified`를 남긴다. 정상 p50/p95/p99는 경로별 시도 분모와 함께, 오류율은 시도한 HTTP 요청 분모로 보고하고 5xx·timeout·연결·JSON/내용 오류를 구분한다. 요청 metric에는 경로 이름과 구간 tag를 사용하고 기본 URL tag는 제외한다. 세션 모드의 tick 시작/완료 counter에는 숫자 `session_slot`을 붙여 활성 사용자별 진행을 비공개로 검증한다. 이 10,000개 tag의 발생기 비용도 실측한다. 정상 관측 창의 도달 RPS/완료 처리량은 timestamp로 잘라 구하며 graceful drain까지 포함한 전체 평균과 구분한다. `active_rounds`, `initialized_sessions`, native `vus`는 서로 다른 값이다. 5초 cadence의 시작/완료 tick을 `session_slot`별로 대조하고 사전 고정한 시계 오차·스케줄 지연 허용폭을 적용해 모든 슬롯이 계속 요청을 만드는지 확인한다. `schedule_delay`·`missed_poll_rounds` 및 기대 tick 대비 실제 시도도 함께 보고해야 10,000 활성 세션의 유지 여부를 판정할 수 있다. 초기화 수나 round 평균만으로 유지 부하를 증명하지 않는다. 전용 자원·입력 무결성·브라우저 보정·계측 중 누락된 항목을 자동 통과시키지 않는다.
