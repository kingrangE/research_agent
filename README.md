# 맥락 · research_agent

정보의 홍수 속에서 오늘·수일 내 주식 투자 판단을 바꿀 새 자료를 찾는 대시보드 시제품입니다. 한국경제의 공개 증권·경제·국제 RSS를 30초마다 수집하고, 기본 화면은 로컬 모델의 시장 맥락순을 표시하며 최신성순도 선택할 수 있습니다. 모델 순위가 아직 없거나 10분 이상 오래되면 기본 추천에 대기 상태를 표시합니다. 최신 자료는 전체 자료에서 확인할 수 있습니다. 제목 키워드는 주제 분류와 필터에만 사용합니다.

## 실행

한국경제 RSS 시제품은 Python 3.10 이상, 추가 설치 없이 실행합니다. 포털 수집·누적 조회·Airflow를 포함한 전체 구성은 아래 Docker Compose 실행 절차를 사용합니다.

```sh
python3 server.py
```

브라우저에서 <http://127.0.0.1:8765>를 여세요. 포트를 바꾸려면 `python3 server.py --port 8766`으로 실행합니다. 실행 환경에서 외부 HTTPS 접속이 허용되어 있어야 합니다. 화면은 5초마다 결과를 확인하며, 수집은 서버가 실행되는 동안에만 동작합니다. 서버를 종료하려면 Ctrl+C를 누르세요.

## 체험할 수 있는 것

- 실제 공개 피드 수집, 동일 링크 중복 제거, 주제별 필터, 검색과 정렬.
- 자료 상세의 선별 이유, 점수 구성, 함께 볼 자료, 원문 링크.
- 기사별 국내·미국 관련 종목과 연결 이유. 직접 언급, 공개된 사업 관계, 공급망 관계, 테마 연관을 구분하고 상세 화면에서 원문 근거·발표일·확인일·추가 확인 조건을 제공합니다.
- 관련 종목의 현재가, 전일 종가 대비 금일 등락률, 제공처의 지연 표기, 거래 기준 시각과 조회 시각. 화면에 보이는 종목부터 조회하고 같은 시세는 10초 동안 재사용합니다. 실패하면 마지막 가격에 이전 조회 표시를 붙이며, 한 번도 조회하지 못한 값은 빈 상태로 표시합니다.
- 브라우저에 저장하는 북마크와 유용성 피드백. 현재 브라우저에만 보관되며, 피드백은 순위에 자동 반영되지 않습니다.
- 수집원별 성공·실패와 마지막 성공 시각. 실패하면 메모리에 남은 마지막 자료를 유지하고 실패 상태를 표시합니다.
- 별도의 **가상 시나리오** 모드. 기사와 리포트 예시임을 표시하며 가짜 원문 링크를 만들지 않습니다. 실제 자료와 저장함도 구분합니다.

## 현재 경계

포털 전체 기사 수집과 상시 수집 작업자·Airflow 역할 분리는 [뉴스 수집 결정 기록](docs/decisions/0001-news-collection.md)에 정리했습니다. 선택한 이유, 대안, 설정의 근거, 장애 복구와 재검토 기준을 기록하며 현재 구현과 앞으로 적용할 설계를 구분합니다.

기본 Python 실행 경로의 자동 수집원은 한국경제의 공개 RSS 3개이며, Docker Compose 구성은 별도 작업자로 Npay 증권 속보 목록도 수집합니다. 네이버 증권 리포트는 원문 사이트 링크만 제공하며 자동 수집은 미연결입니다. RSS의 모든 유효 항목을 추천 여부와 무관하게 수집하고 원래 RSS 항목 XML·제목·링크·발행 시각 등을 보관합니다. PDF 분석, 여러 매체 교차 검증, 환율·거래량과 주도주 판별은 아직 제공하지 않습니다. 아래 선택적 분석을 켜면 지원하는 한국경제·네이버 뉴스의 공개 추출 본문을 사용합니다. 로그인·유료 전문은 지원하지 않으며 공개 추출 내용이 전문 전체인지는 보장하지 않습니다.

관련 종목은 KRX KIND와 Nasdaq Trader의 NASDAQ·NYSE 상장 목록을 대조합니다. 목록은 서버 시작 시 조회하고 성공 시 하루에 한 번, 실패 시 5분 후 재시도합니다. ETF·우선주·워런트·유닛 등은 제외하며 미국 특수 종목과 일부 ADR은 누락될 수 있습니다. 한 상장 목록의 조회가 실패해도 다른 시장의 성공한 목록과 마지막 성공 자료는 유지합니다. 본문에서 추출한 이름은 근거 문장에서도 같은 종목으로 직접 확인돼야 연결합니다. 이름 일부만 겹치는 우선주·계열사나 동명이인·인용 표기를 걸러내는 기존 문맥 검사를 본문 연결에도 적용하며, 함께 등장한 다른 회사를 임의로 추가하지 않습니다. 이는 이름 대조의 보완이며 모든 동명이인이나 문장 속 당사자 역할을 판별한다는 보장은 아닙니다.

AI 영역은 공개 연구·기업 발표·정부 자료를 검토한 `data/relations.json`의 12개 기업 프로필과 16개 관계로 확장합니다. 회사가 직접 언급되어도 거래 상대방·메모리·파운드리·가속기·클라우드·LLM·기업용 서비스 연결을 함께 찾습니다. 직접 언급된 회사를 보존하고 공개 관계를 우선하여 최대 8개 후보를 제시하며, 기사에는 주식명과 등락률만 작은 버튼으로 표시하고, 해당 주식을 누르면 가격·거래 기준 시각·연결 근거를 모달에서 확인합니다. 근거가 같은 단계에서는 시장과 역할을 분산합니다. 직접 언급이 8개를 넘으면 모두 유지합니다. 정책 지원 대상, 투자금의 실제 사용처, 계약과 계획의 차이, 매출 기여는 확인 조건으로 남기며 주가 방향은 단정하지 않습니다. 비상장 OpenAI·Anthropic에는 가짜 종목코드를 만들지 않습니다. 기사 발행 이후에 발표된 관계 근거는 제외하지만 완전한 과거 시점 재현용 데이터는 아닙니다.

풍부한 관계 근거를 구축한 범위는 AI이며, 제목과 사전 검토 자료를 사용하는 규칙 기반 구현입니다. 모든 산업을 포괄하거나 기사마다 새로운 조사를 실행하는 모델은 아닙니다. AI 외에는 방산·원전·정유 등 제한된 주요제품 규칙을 유지합니다. 범위가 넓은 환율·전쟁 이슈에는 임의의 종목을 연결하지 않습니다. 동명이의어·축약명·기사 말미의 증권사 출처를 일부 걸러내지만 누락과 오연결이 가능합니다. [방법론·조사 결과](https://app.notion.com/p/415ab4402a318100b6f0f634e45f7e17)를 함께 확인하세요.

시세는 Npay 증권 공개 응답을 사용하며 거래 기준 시각·장 상태·제공처의 지연 표기를 함께 취급합니다. 국내 가격은 원화, 미국 가격은 달러로 표시하며 미국 시세는 정규장 기준입니다. 미국 시간외 시세는 제공하지 않습니다. 지연 표기는 제공처의 값이며 도착 지연을 독립적으로 검증한 결과가 아닙니다. 비공식 공개 경로이므로 구조 변경이나 접근 제한으로 조회가 중단될 수 있습니다. 가상 시나리오에서는 실제 시세를 조회하지 않습니다. 기존 북마크는 저장 당시 내용이어서 새 관련 종목 정보를 얻으려면 최신 자료에서 다시 저장해야 합니다.

최신성은 발행 직후 50점, 30분 후 37.5점, 60분 후 25점이며 첫 60분 동안 선형으로 감소합니다. 60분 이후에는 시간당 1점씩 연속 감소하여 2시간 후 24점, 26시간 후 0점이 됩니다. 발행 시각이 없으면 최신성은 0점이며 미래 발행 시각은 50점으로 제한합니다. 최종 점수는 최신성만 사용하며 소수점 첫째 자리로 반올림합니다. 주제·리포트 가점은 없고 같은 주제의 키워드 수와 주제 수는 점수에 영향을 주지 않습니다. 이는 시제품의 읽기 순서이며 투자 가치·신뢰도·주가 방향을 나타내지 않습니다. 연결 설명은 일반적인 확인 경로이며 기사 내용의 인과관계를 분석한 결과가 아닙니다. 제목이 비슷해도 URL이 다르면 보존하며, 사건 묶기는 본문 분석 단계에서 수행합니다.

연결된 RSS의 전체 유효 항목과 변경 이력은 `.data/news.sqlite3`에 누적 저장합니다. 일반 금융 뉴스·상품 안내·행사도 수집하며 동일 링크 중복 제거와 추천 제외는 보관 후 화면 단계에서 적용합니다. 공개 추출 본문은 LLM 사용 여부와 무관하게 별도 작업자가 초당 최대 1건씩 수집하고, 성공·실패·재시도 상태와 본문 변경 이력을 보관합니다. 본문 보관에는 모델의 6,000자 입력 제한을 적용하지 않습니다. 재시작 시 수집원별 마지막 성공 피드를 복원한 뒤 새 자료를 확인합니다. 수집 시작 전 피드에서 빠진 과거 기사·실행 중단 기간 전체의 기사·로그인 및 유료 전문·과거 순위의 완전한 재현은 지원하지 않습니다. 자동 삭제나 추천 필터에 따른 원본 삭제는 하지 않습니다. 제공자가 피드 구조나 접근 정책을 변경하면 수집에 실패할 수 있습니다. 수집은 30초마다 시작하며, 수집 소요 시간·화면 확인 간격·제공자 RSS 반영 지연이 추가됩니다. 초 단위 속보 도착을 보장하지 않습니다. 운영 서비스로 확장하기 전 각 제공자의 수집·저장·재배포 조건을 확인해야 합니다.

## 로컬 본문 분석 · 사건 묶기 · 시장 맥락순

추천 목록 위에는 이번 분석 대상 기사 수와 현재 읽기 기준의 본문 분석 건수를 표시합니다. 순위 계산이 성공해도 미분석 기사가 남으면 이를 명시합니다. 분모는 이번 분석에 전달된 기사이며 누적 보관 기사 전체가 아닙니다. 본문 분석 건수는 사건 수·주식 적합성 판정 완료 수·최종 추천 수와도 다르므로 분석 완료 자료 내의 참고 순위로 해석해야 합니다.

Ollama에 이미 설치된 8B 이하 모델을 사용합니다. 기본 모델은 `ax4-light:latest`이며 다운로드나 학습은 자동으로 하지 않습니다. Ollama 로컬 서버가 실행 중일 때 다음과 같이 시작합니다.

```sh
python3 server.py --analysis
```

다른 설치 모델은 `LLM_MODEL` 환경변수로 지정합니다. 모델별 호환성과 라이선스를 확인하세요. A.X 4.0 본체는 72B이므로 이 실험에서는 Light 7B를 대상으로 합니다. 추론용 GGUF를 그대로 학습시키는 방식은 아니며, 향후 LoRA 학습은 원본 체크포인트와 별도 학습 환경이 필요합니다.

분석은 백그라운드에서 공개 본문을 읽고 사건·당사자·확정 여부·금액·시점·원문 인용을 추출합니다. 최근 사건들과 의미를 비교해 같은 사건을 묶고, 별도 모델 호출이 현재 시장 맥락과 사건을 비교해 읽기 순서를 제안합니다. 업종별 고정 가점은 없습니다. 별도 임베딩 모델 대신 작은 LLM이 제한된 후보 안에서 사건 일치 여부를 판별하는 초기 구현입니다. 단순 같은 테마, 신규 계약, 부인과 정정은 서로 다른 사건으로 취급하도록 요청하지만 확정 상태가 바뀌거나 취소·부인·철회 등 반대 행동이 나타나면 기존 사건 연결을 끊습니다. 의미 판정 자체의 정확도는 별도 검증이 필요합니다.

**시장 맥락순 · 실험**이 기본 선택입니다. 화면의 자료 정렬에서 최신성순으로도 바꿀 수 있습니다. 분석된 사건 중 오늘·수일 내 주식 판단에 쓸 구체적인 변화가 확인되는 사건만 대표 기사로 추천합니다. 상품 안내·행사·배경 기사·연결 미확인·미분석 자료는 기본 추천을 채우지 않으며 전체 자료에서 확인합니다. 기본 최신성 점수는 변경하지 않습니다. 모델 분석·근거 문장·함께 묶인 원문은 기사 상세에서, 입력 시장 관측은 수집 현황에서 확인합니다. 새 순위 응답이 실패하면 원문 근거·시장 관측·분석 기준이 같은 경우에만 10분 이내의 마지막 성공 순위를 생성 시각과 일부 분석 표시를 붙여 유지합니다. 입력이 바뀐 사건의 예전 이유는 재사용하지 않습니다. 순위가 없거나 10분 이상 오래되면 기본 추천에는 분석 대기 상태를 명시합니다. 전체 자료 또는 최신성순 선택에서 최신 기사를 볼 수 있습니다. 검토 결과 주식 판단 재료가 0개인 경우에도 배경 기사로 추천을 채우지 않습니다. 가상 시나리오에는 실제 모델 분석을 혼합하지 않습니다.

시장 맥락은 Npay의 국내 KOSPI200·KOSDAQ150 ETF와 미국 S&P500·업종 ETF 가격 변화를 사용합니다. 미국 업종의 S&P500 대비 변화는 거래 날짜가 같을 때만 계산합니다. 장마감 시각과 누락 자료를 보존하며 미국과 국내 가격을 같은 거래 시간의 움직임으로 취급하지 않습니다. 거래대금·상승 확산도·환율·금리는 아직 입력하지 않으므로 완전한 시장 국면 판별기가 아닙니다.

본문과 분석은 `.data/analysis.sqlite3`에 저장합니다. `analysis_store.py`는 SQLite 트랜잭션으로 작업 등록·처리 권한·재시도와 기사/본문 버전별 분석 근거를 관리합니다. 보관소의 RSS·본문 변경 기록을 각각 100개씩 이어 읽으며, 추천 여부나 현재 RSS에 남아 있는지와 무관하게 대기열에 넣습니다. 본문 변경 후 이전 내용으로 돌아온 경우도 별도 관측 버전으로 남기고, 같은 내용의 반복 수집은 새 작업을 만들지 않습니다. 기존 보관소에 관측 순서가 없던 자료는 최초 저장된 본문들과 마지막 상태로 초기화하므로 그 이전의 모든 변경 순서를 복구하지는 못합니다.

분석은 한 건을 마칠 때마다 화면 결과를 다시 구성합니다. 대기 작업이 남아 있으면 1초 뒤 다음 작업을 이어가고, 대기가 없으면 기존 유휴 확인 간격을 유지합니다. 외부 API의 일일 상한에 도달하면 짧은 간격으로 작업을 반복하지 않습니다. 처리 순서는 오래 기다린 작업 1개, 발행 시각이 최신인 작업 2개를 반복합니다. 실패한 작업은 5분부터 최대 60분까지 대기 후 다시 시도하고, 중단된 처리 권한은 최대 5분 뒤 회수합니다. 재시작해도 대기·실패·완료 상태와 보관소 읽기 위치를 유지하며, 같은 버전을 중복 등록하지 않습니다. 뒤늦게 완료된 이전 버전이 최신 본문 분석을 대신하지 않습니다. 수집 현황에서 대기·처리 중·재시도·완료 버전·보관 사건·최장 대기·최근 100건 처리 지연 p95를 확인합니다. 전체 작업의 처리 지연은 등록부터 완료까지이며 과거 자료와 재검토를 포함합니다. 별도로 발행 1시간 내 등록한 기사 버전별 일반 분석의 최근 1시간 완료 표본 최대 100건에서 발행→분석 완료 p50·p95를 확인할 수 있습니다. 이 값도 최종 추천 공개 시간은 아닙니다. 미완료 집계는 오래 지연돼도 남기며 기사 고유 수가 아닌 버전별 작업 수입니다. 모델 요청은 같은 모델의 최근 측정 최대 100회에서 본문·적합성·순위별 응답 대기 시간을 표시하고, 서버 대기·통신·시간 초과를 포함합니다. 과거 미측정 호출은 0초로 채우지 않습니다. 누적 보관소를 처음 읽는 동안에는 아직 대기열에 옮기지 않은 자료가 있을 수 있습니다.

본문 읽기 또는 영향 판정 기준이 바뀌면 두 기준 중 하나라도 맞지 않는 기존 분석은 현재 추천에서 제외하고, 최근 26시간 이내 후보를 순차 재검토합니다. 일반 분석 3건마다 재검토 1건에 차례를 주며 일반 작업이 없으면 바로 진행합니다. 호환되는 본문 분석은 재사용하고 이전·새 판정을 별도 이력으로 보존합니다. 재검토 시각으로 기사 발행 시각을 바꾸지 않으며, 전체 기사에서는 계속 원자료를 볼 수 있습니다. 읽기 기준만 바뀌어도 최근 후보를 다시 분석하며, 과거 전체 기사를 일괄 재분석하지는 않습니다. 재검토 이력의 시각은 캐시의 예전 판정 시각이 아닌 이번 작업의 완료 시각입니다.

사건 비교는 저장된 최근 분석 500개에서 당사자·제목의 공통 단어로 최대 6개 후보를 찾은 뒤 기존 LLM이 판단합니다. 별도 임베딩 검색은 아직 도입하지 않았습니다. 같은 기사의 다른 버전은 과거 분석을 지우지 않고 이력으로 연결하며, 기사 시각 이후의 사건을 비교 후보로 넣지 않습니다. 기사 상세의 ‘자세히 보기’에서 최근 이력 10개와 당시 요약·상태·금액·시점·원문 링크를 확인할 수 있습니다. 이력 전체는 저장소에 유지합니다. 모델 입력은 각 공개 본문 앞부분 최대 6,000자이며, 그 뒤의 변경 사실까지 분석했다고 보장하지 않습니다.

화면의 5초 조회는 모델을 실행하지 않습니다. 현재 피드에서 분석을 마친 사건 중 주식 적합성을 통과한 최근 최대 12개를 시장 맥락으로 재정렬합니다. 이 후보 수 제한은 전체 수집·대기열 처리 제한과 별개입니다. 시장 맥락과 순위는 새 사건 발생 또는 약 5분 간격으로 갱신합니다. 로컬 추론 중에도 최신성 목록은 계속 응답합니다. 로컬 모델은 토큰 API 요금이 없지만 실행 장비·전력·지연 비용이 있습니다.

로컬 Ollama에는 일일 호출 제한을 적용하지 않으며 `LLM_DAILY_CALL_LIMIT`도 무시합니다. 요청 수·토큰 사용 기록은 재시작 후에도 보존합니다. 기존 단일 분석 작업자, 회차별 처리량과 실패 후 재시도 대기는 유지합니다. 외부 Gemini API에만 기본 일일 200회 상한을 적용하며 실패도 포함합니다. 외부 API의 상한은 `LLM_DAILY_CALL_LIMIT`로 조정할 수 있고 달러 금액의 예산을 보장하지 않습니다. 현재 사용 기록은 제공처별로 나뉘지 않으므로 같은 저장소에서 제공처를 바꾸면 이전 로컬 요청도 외부 API의 상한 계산에 포함됩니다. 모델 응답의 필드, 원문 인용 존재 여부, 사건 ID, 순위의 누락·중복을 검증하고 실패한 분석은 채택하지 않습니다. 검증 통과가 요약과 해석 전체의 사실성을 보장하지는 않습니다.

선택적으로 `LLM_PROVIDER=gemini`, `LLM_MODEL=gemini-3.5-flash-lite`, `GEMINI_API_KEY`를 서버 환경변수로 설정하면 Gemini 비교 실행도 가능합니다. 이 경우 기사 추출 내용이 해당 API로 전송되고 요금이 발생할 수 있습니다. 기본은 로컬 Ollama이며 다른 제공처로 자동 전환하거나 실패 시 비싼 모델을 호출하지 않습니다. 비밀 값은 브라우저나 저장소에 넣지 마세요.

모델 비교는 다음 명령으로 실행합니다. 설치된 모델만 사용하며 기본 테스트 자료는 개발자가 만든 가상 기사입니다. 실제 금융 정확도·수익률·전문가 정답 평가를 뜻하지 않습니다. 실행 시 로컬 모델을 사용하며 `LLM_PROVIDER=gemini`를 설정한 경우에는 API 요청이 발생합니다.

```sh
python3 evaluate_models.py --models ax4-light:latest exaone3.5:7.8b
```

검증 결과와 실패 응답은 `.data/model-evaluation.json`에 남습니다. 파인튜닝은 현재 수행하지 않습니다. 실제 기사 표본에서 모델 간 비교와 프롬프트·근거 입력 개선을 먼저 검증하고, 반복되는 작업 오류가 남을 때만 검수된 정답으로 LoRA 등 작업별 학습을 검토합니다. 시장의 최신 사실은 학습 가중치 대신 갱신되는 입력으로 전달합니다.

최종 순위만 격리해 비교하려면 아래 명령을 사용합니다. 운영과 같은 원문 입력·정책·응답 검증을 사용하고, 가상 적합성 사례 9건과 계약·실적·부인 본문 3건을 사건 ID로 연결해 검사합니다. 시장 관측은 비우며 수집·본문 읽기·전단계 적합성은 실행하지 않습니다. 분류 점검 결과와 호출·출력 토큰 증가량, 입력 및 자료 파일 지문을 기록합니다. 순위가 반환한 순서와 평가 자료 순서가 달라도 ID로 비교합니다. 명령의 성공 종료는 결과 저장을 뜻하며 품질 기준을 모두 통과했다는 뜻은 아닙니다. 기대 분류는 개발자 기준으로 전문가 정확도나 투자 성과 점수가 아닙니다.

```sh
LLM_PROVIDER=ollama python3 evaluate_models.py --ranking-only --models ax4-light:latest --output .data/ranking-quality.json
```

주식 추천 적합성은 LLM이 사건별로 `주식 판단 재료`, `배경·상품 안내`, `연결 미확인`으로 구분합니다. 업종별 고정 점수가 아니라 기업·산업의 이익·수주·비용·자본·규제·수급을 바꿀 구체적인 사실과 전달 경로를 요구합니다. 개인투자용국채 정기 청약처럼 판매사의 실적 변화 근거가 없는 상품 안내는 추천에서 제외합니다. 반대로 예상 밖 금리 충격이나 상장사의 차환 실패처럼 주식 판단에 영향을 주는 채권·금리 사건은 후보로 유지합니다. 추천 사유에는 전달 경로와 다음 확인 사항을 표시하며, 판단 자료가 없으면 임의의 매수·매도 시점을 생성하지 않습니다. 배경 판정도 모델의 오류가 있을 수 있으므로 전체 자료를 삭제하지 않습니다.

적합성 검토는 다른 기사와 섞어 순위를 매기기 전에 사건별로 독립 실행하고 저장합니다. 이후에는 통과한 사건끼리만 순위를 매깁니다. 이 분리로 다른 후보가 바뀌었다는 이유로 상품 안내가 주식 재료로 승격되는 문제를 줄입니다. 적합성 판단도 모델 추론이며 완전한 사실 검증은 아닙니다. 검수 전의 추천이므로 전체 자료를 보존합니다. 적합성 검토에도 로컬 모델 요청이 사용되며 동일 사건·모델·기준은 재사용합니다.

```sh
python3 evaluate_models.py --equity-only --models ax4-light:latest --output .data/equity-evaluation.json
```

위 평가는 국채 청약과 수상 같은 배경 정보, 예상 밖 금리 충격·차환 실패·실적 전망 하향을 구분하는 개발용 가상 대조군이며 전문 투자자의 정답 평가나 수익 검증은 아닙니다.

추천과 수집은 별개입니다. 기본 추천에서 제외된 자료도 RSS 원본과 공개 추출 본문을 보관해 이후 시장 맥락 분석에 재사용할 수 있습니다. 수집 현황에서 누적 기사·RSS 기록·본문 성공·대기·실패 건수를 확인합니다. 수집 범위는 연결된 한국경제 RSS 3개와 Npay 증권 속보 목록이며 모든 언론사나 해당 사이트의 과거 전체 기사까지 수집했다는 의미는 아닙니다.

현재 추천에서는 사건의 최초 확인 발행 시각이 26시간을 넘거나 미래·미확인이면 제외합니다. 26시간은 기존 최신성 점수가 0이 되는 경계입니다. 같은 사건의 재전송은 최초 발행 시각을 갱신하지 않으며, 새 변화는 별도 사건으로 분석합니다. 이는 원본 수집·보관을 제한하지 않습니다. 공개 본문에서 실제 이름과 인용이 확인된 상장사는 제목에 없어도 `본문 언급`으로 연결하되, 사건의 수혜·피해나 당사자 역할을 확정하지 않습니다. 제목이 바뀌고 새 본문이 준비되지 않았으면 이전 본문 분석을 재사용하지 않습니다.

쇼핑백·로고 개편의 막연한 고객 유입 기대는 홍보로 구분하고, 실제 수수료 조건 변경은 비용·수익 변화 후보로 유지합니다. 적합성 모델에는 경제적 변화의 원문 인용을 요구합니다. 인용이 없으면 추천에 올리지 않고, 제시한 인용이 입력 근거에 없으면 판정을 채택하지 않습니다. 기사 안에 문장이 존재한다는 검증이며 주장·해석의 진위 전체를 검증하지는 않습니다. `python3 evaluate_models.py --equity-only`는 시장 조회·순위 호출 없이 적합성만 평가하며, 개별 실패를 기록하고 다음 표본을 계속 검사합니다.

시세 조회는 공유 작업자 최대 4개와 대기 작업 최대 20개로 제한하며, 같은 종목의 진행 중 요청을 재사용합니다. HTTP 응답은 시세를 최대 5초 기다린 후 진행 중 상태나 이전 시세를 반환합니다. 공급자 요청은 백그라운드에서 마무리되며, 이전 가격은 원래 시각과 이전 조회 표시를 유지합니다. 이 제한은 API 대기열 제어이며 로컬 LLM의 일일 호출 상한이 아닙니다.

같은 기사 목록은 5초 확인 때마다 HTML을 다시 생성하지 않으며, 내용·정렬·표시 시세가 달라진 경우에 갱신합니다. 새 정보가 들어오면 목록은 바뀔 수 있으므로 읽던 상세는 별도로 유지합니다.


## 포털 수집과 Airflow 실행

Docker Compose는 대시보드, 10초 간격의 Npay 증권 목록 작업자, 5분 간격의 Airflow 복구 작업을 실행합니다. 포털 경로는 화면이 사용하는 공개 요청이며 정식 개발자 API나 제공 지연 보장 계약이 아닙니다. RSS 3개는 계속 보완 수집합니다. 목록 확인은 최대 3페이지씩 수행하고, 첫 페이지를 다시 확인하면서 미완료 페이지를 이어 읽습니다. 요청 사이에는 1초 대기하며 오류 시 30초부터 최대 15분까지 재시도 대기를 늘립니다. 접근 거부·요청 과다에는 최소 15분과 제공자의 재시도 안내를 적용합니다. 실행 간격은 제공처 조건과 실제 지연을 보고 조정할 초기 설정입니다.

처음에는 `.env.example`을 참고해 `.env`에 현재 사용자의 숫자 UID를 `AIRFLOW_UID`로 설정하세요. UID는 `id -u`로 확인합니다. 이후 다음 명령으로 시작합니다.

```sh
docker compose up -d
```

대시보드는 http://127.0.0.1:8765, Airflow는 http://127.0.0.1:8089 에서 접근합니다. Airflow는 공식 3.4.0 이미지의 개발용 standalone 구성이며 운영 배포 구성은 아닙니다. 인증 정보는 전용 볼륨 안의 Airflow 생성 파일에만 남습니다. 직접 로그인할 때 `docker compose exec airflow cat /opt/research/.data/airflow/simple_auth_manager_passwords.json.generated`로 확인할 수 있으며 저장소나 채팅에 복사하지 마세요. 중지는 `docker compose stop`입니다. 볼륨 삭제 명령은 사용하지 마세요.

모든 서비스는 같은 Linux 전용 Docker 볼륨에서 SQLite를 사용합니다. Mac 호스트 프로세스와 Linux 컨테이너가 같은 SQLite 파일에 동시에 쓰는 구성은 사용하지 않습니다. 초기화 작업은 호스트의 기존 자료를 무결성 검사 후 최초 한 번 이관하고, 이미 데이터가 있으면 덮어쓰지 않습니다. 무결성이 잘못된 자료는 시작을 중단합니다. Docker 구성을 사용하는 동안 별도의 호스트 `python3 server.py`나 수집 작업자를 동시에 실행하지 마세요. 호스트의 `.data`는 이관 시점의 원본이며 실행 중 데이터는 Docker 볼륨 안에 있습니다. 로컬 Ollama는 컨테이너에서 `host.docker.internal:11434`로 접근하고, 모델 다운로드나 외부 유료 API 전환은 수행하지 않습니다.

`전체 자료`는 누적 보관소의 최신 기사 버전을 URL별로 조회합니다. 추천 여부나 분석 완료 여부로 제외하지 않으며, 같은 사건의 서로 다른 기사도 각각 표시합니다. 최신순 페이지 이동, 제목·언론사 검색, 언론사·한국시간 날짜·주제·자료 유형 필터를 지원합니다. 제목·본문의 과거 수정 버전은 보관하지만 기본 목록에 수정 버전을 각각 별도 기사로 늘어놓지는 않습니다. API는 `/api/articles`이며 30건씩 커서로 이동합니다. 날짜·언론사·검색은 현재 페이지 안에서만 거르는 방식이 아니라 누적 보관소 전체에 적용합니다.

Airflow의 `news_reconciliation`은 오늘과 이전 날짜·남아 있는 오래된 미완료 날짜를 최대 100페이지씩 읽고 저장 위치에서 다음 실행을 이어갑니다. 날짜별 초기 자료가 30페이지를 초과하는 것을 실제로 확인해 복구 작업 예산을 100페이지로 늘렸으며, 짧은 수집 작업의 3페이지 제한과는 별개입니다. 진행 중에는 상시 작업자가 첫 페이지를 별도로 저장하므로 복구 작업 완료를 기다리지 않습니다. Airflow 작업은 30초 후 최대 두 번 재시도하며 제공자의 재시도 대기는 별도로 존중합니다. 구간이 아직 남았거나 요청이 실패하면 성공으로 처리하지 않고 재시도합니다. 원본이 제공하지 않는 날짜는 소급 복구할 수 없으며 전체 매체의 전문이나 무누락을 보장하지 않습니다. 본문은 공개된 한국경제·네이버 뉴스 기사만 추출하고 실패·비공개·유료 내용은 실패 상태로 남깁니다. 포털 표시 시각을 원문 발행 시각과 동일하다고 보장하지 않습니다.

현재 실행 검증은 Mac Docker Desktop 환경에서 수행했습니다. Linux 서버 배포 시에는 로컬 Ollama 접근 주소와 네트워크 경로를 별도로 검증해야 합니다. 초기 호스트·컨테이너 공유 파일에서 관찰한 무결성 오류, 원본 보존·복구·Linux 전용 볼륨 이관 이유와 검증 범위는 위 결정 기록의 구현 절에 남겼습니다.


## 2026-11-13 분석·화면 지연 점검

원문 복사 대신 현재 기사 앞부분의 원문을 240자 단위 구간으로 나누어 모델에 제공하고, 모델이 선택한 구간 번호를 코드가 실제 원문으로 치환합니다. 짧은 마지막 조각은 앞 구간에 붙여 원문 전체가 보존되도록 하며, 존재하지 않는 번호·중복·잘못된 타입·원문에 없는 인용은 거부합니다. 선택된 원문이 정확하다는 것과 요약·투자 해석이 정확하다는 것은 별개입니다. ‘추진 발표’와 ‘정책 시행 확정’을 구분하는 단계 설명을 보강했고 후속 소수 실제 호출도 확인했습니다. 검증 범위와 실패·남은 해석 오류는 [결정 기록](docs/decisions/0001-news-collection.md)에 보존하며 전문가 정확도가 검증된 것은 아닙니다. 새 읽기 기준은 캐시 키와 결과에 구분해 기록하고 이미 완료된 대기열·과거 이력을 일괄 삭제하거나 새 대기열로 재등록하지 않습니다.

기존 인용 검증 실패 이력이 있는 실제 기사 4건을 같은 본문으로 비교했을 때 기존 복사 방식은 1건, 구간 선택 방식은 4건이 인용 검증을 통과했습니다. 당시 비교 사건 입력까지 재현한 실험은 아니고 각 방식 1회뿐이므로 일반 정확도·속도 향상을 뜻하지 않습니다. 구간 선택 후에도 정책 추진을 확정으로 표현한 해석 오류를 관찰해 단계 지시문을 추가 수정했습니다. 이후 기준까지 4건 모두 정확했다고 보고하지 않습니다.

대시보드·누적 기사 요청에도 기존 시세 요청과 같은 15초 중단 조건을 적용합니다. 통신 실패 시 로딩 상태를 풀어 다음 확인이 가능하도록 하고, 마지막으로 받은 순위가 10분을 넘었는지는 브라우저에서도 판단해 오래된 추천을 계속 표시하지 않습니다. 실제 운영 중 정적 파일·API가 10초 안에 응답하지 않는 사례가 있었으며, 저장소의 단순 조회는 짧았습니다. Airflow를 잠깐 분리한 관찰로는 원인을 확정하지 못했고 실행은 재개했습니다. 원문 선택·한 건씩 결과 공개·화면 요청 제한의 회귀 검증을 통과한 것과 운영 지연 원인 전체를 해결한 것은 구분합니다.
